# Synthetic seed provenance and safety

The base and advanced seeds are locally authored synthetic construction scenarios. The company is explicitly named **Sitecraft Synthetic Demonstration Ltd.** People, vendors, quantities, accounts, schedules, invoices and financial settlements in these fixtures are fictional; none are actual customers, users or bank transfers.

The local PostgreSQL demonstration currently contains 7 role accounts, 1 project, 2 sites, 20 BOQ items, 7 budgets, 11 linked tasks, 8 progress records, 6 workers, 6 attendance records, procurement/material/contract/commercial scenarios and notifications. There are 9 cost-ledger rows and 5 stock balances. Advanced financial fixtures are generated through the application's real validation/approval workflows; opening balances are explicitly tagged. Data is persisted in the `sitecraft-readiness-pg` local Docker volume. The separate browser/jobs test databases are isolated fixtures, not production storage.

`npm run db:seed` runs both seeds. Base fixture IDs are stable. Advanced records use stable natural keys and retain their initially persisted IDs. A completed advanced seed writes a unique completion marker; subsequent runs return without changing schedules, approvals, payments or real business edits. Advanced examples use a fixed reference date. If a company already exists under the base namespace, the base seed leaves it alone; advanced seeding refuses to run unless the explicit synthetic tenant provenance is present. Legacy seed companies are not silently renamed or upgraded.

Reruns never reset passwords. `npm run db:seed:verify` snapshots every business table, reruns the scripts and asserts identical rows, including IDs/password hashes; run it after initial seeding without concurrent writers. Missing/deleted records in a completed seed are intentionally not recreated. Base insertion is one transaction. Advanced seeding is resumable through validated natural-key checks and a completion marker, not one global transaction; run only one seed process at a time, and back up before retrying an interrupted advanced seed.

`SEED_PASSWORD` is required for initial local creation, must be sufficiently long and must fit bcrypt's UTF-8 byte limit. Local sample roles initially share that operator-supplied password, so this is an isolated development fixture. In production, all newly seeded sample accounts receive random discarded password hashes, including the company administrator, and execution requires explicit `ALLOW_PRODUCTION_SEED` approval. Existing accounts/passwords are never changed by a rerun: operators must review any old seed accounts before connecting an existing production database.

Create a real privileged account in a separate company with `npm run admin:bootstrap`, using `BOOTSTRAP_COMPANY_NAME`, `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` supplied securely. This script refuses an existing email and never resets passwords or escalates existing accounts. Remove bootstrap variables afterwards. Do not grant known passwords to synthetic privileged accounts to operate a real company.

Private seed rows never enter public HTML, localStorage or static frontend data. The login/loading shell is available before the API is ready. Project snapshots require a real authenticated, authorized response and are kept only in memory.
